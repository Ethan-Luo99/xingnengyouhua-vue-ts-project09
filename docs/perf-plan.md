一、场景拆解

0. 统一事实基线（三种场景共用的调度器行为，先固定术语）

0.1 一次响应式写入到 DOM 更新的完整链路是：组件事件回调或业务代码中对 ref/reactive 赋值 → reactivity 层 dep.notify() 把受影响的 ReactiveEffect 批量收集 → 有 scheduler 的 effect 调用 queueJob(job) 入队 → queueFlush() 安排一个 Promise.resolve().then(flushJobs) 微任务 → 当前同步代码结束后的微任务检查点统一执行 flushJobs：先跑 pre 队列（默认 watch/watchEffect），再跑组件渲染 job（执行渲染函数生成 vnode 并 patch 到 DOM），最后跑 post 队列（flush:'post' 的 watch、onMounted/onUpdated、模板 ref 赋值）。

0.2 去重与排序：queueJob 用 job.flags 的 QUEUED 位去重，同一 tick 内对同一组件依赖的几百次写入，其渲染 job 在队列中只有一个；队列按 job.id（组件 uid）排序，父组件先于子组件；pre 回调带 PRE 标记位且 id 绑定所属组件 uid，在该组件渲染前被 flushPreFlushCbs 取出执行；post 回调在 flushPostFlushCbs 中用 Set 去重并按 id 排序。

0.3 watch 的三种 flush 在源码中的真实分流：默认 flush:'pre' 的 scheduler 是 queueJob，但首次运行（isFirstRun）直接 job() 立即执行，后续变更才入队；flush:'post' 的 scheduler 是 queuePostRenderEffect（进 post 队列，DOM 更新后才跑）；flush:'sync' 不挂 scheduler，依赖一变就在触发写入的同一调用栈里立即执行。

0.4 computed 在 3.5 的脏检查是版本号机制而非每次重新执行：ComputedRefImpl 持有 globalVersion 快照，全局任何响应式变更都会自增全局 globalVersion；读取 .value 时 refreshComputed 先比对版本，版本未变直接返回缓存值；版本变了才执行 getter，且只有 getter 返回值 hasChanged（Object.is 不等）时才自增自身 dep.version 向订阅者传播。换言之：computed 是惰性的（没人读就不重算），且"值实际没变"的 computed 不会触发下游渲染。

0.5 SFC 编译器事实：@vue/compiler-sfc 编译 SFC 时默认 cacheHandlers: true。不引用 v-for 迭代变量/v-slot 作用域变量、且不是成员表达式透传的内联事件处理器会被编译进渲染函数的 _cache，多次渲染复用同一函数引用；反之，列表项里捕获了循环变量的行内处理器每次渲染都是新函数。

1. 场景 (a)：页面初始化/挂载阶段集中执行几百个函数

1.1 调用发生在哪个阶段。app.mount() 的首次挂载是一条同步深调用栈，不经过 scheduler：mountComponent 中同步执行 setupComponent（即 setup() 函数体），随后在 setupRenderEffect 里对初始挂载直接 effect.run() 同步执行 componentUpdateFn，父组件 patch 子组件时递归进入子组件的 setup 与首次渲染。因此几百个函数如果直接写在 setup 顶层、setup 顶层立即调用的工具函数、或同步注册时立即执行的 watch(..., { immediate: true }) 与 watchEffect（二者首次运行都是同步的），全部叠加在挂载这一个任务的 self time 里，阻塞首次绘制。onMounted/onBeforeMount 这类钩子是 post/pre 队列回调，在微任务中执行，仍早于首帧绘制——把活挪进 onMounted 并不能让出首帧，必须再让出一个宏任务。

1.2 与响应式系统的交互。初始化阶段的典型放大点有四处：其一，对大体量数据调用 reactive()/ref() 后立刻做几百次结构性遍历，Proxy 的 get/set 拦截与依赖收集按属性访问次数计费；其二，注册几百个 watcher 时，watchEffect 与 immediate watch 的首次运行会立即建立完整依赖图（deep:true 还会在取值阶段 traverse() 整个可达对象图，成本与对象规模同阶）；其三，setup 中若互相写入响应式状态，可能在微任务 flush 之前形成多轮 pre 回调—写入—再调度（flushJobs 对同一 job 有约 100 次的递归更新保护，超限直接抛错）；其四，几百个函数若各自 new 一份闭包数组/监听器且没有统一销毁入口，后续卸载成本与内存压力在初始化时即被埋下。

1.3 主线程瓶颈定位。按任务构成拆：setup 同步计算（纯 CPU self time）→ 渲染函数执行（创建几百至几千个 vnode 的 JS 开销）→ patch（创建 DOM 节点、设置属性、appendChild；此时通常还不触发 reflow，但穿插 getBoundingClientRect 类强制布局读取会立刻产生 layout 成本）→ post 队列（mounted 钩子里的初始化代码）。首帧前出现一个 50ms 以上的 Long Task 时，Performance 面板中 self time 最高的叶子函数属于哪一段，优化手段完全不同，不能合并处理。

2. 场景 (b)：用户单次交互触发几百个函数连锁执行

2.1 调用发生在哪个阶段。一次点击/输入的时序是：浏览器派发输入事件（一个任务）→ 事件回调（经 SFC 缓存的处理器，或列表中未缓存的新函数引用）执行，这是交互的 processing 段起点 → 回调内的响应式写入 → 微任务检查点执行 flushJobs：pre watcher（按组件 uid 排序，可在其中读到更新前的 DOM）→ 各受影响组件的渲染函数 → patch（DOM 增删改）→ post 回调（updated 钩子、需要 DOM 尺寸的逻辑）→ 浏览器在下一帧渲染前执行样式/布局/绘制。INP 统计的就是从输入事件开始到下一帧呈现的整段时长。

2.2 与响应式系统的交互。渲染 job 去重对"单个大组件被改了几百次"是友好的：无论写入多少次，该组件 render job 只执行一次。但去重不覆盖三种放大：其一，几百次写入若分别命中几百个不同 watcher 的 source，就是几百个不同的 pre job，一个都不会被合并；其二，watch 链式互写（A watch 后写 B，B 的 watch 再写 C）在同一个 flush 内产生多轮调度，延迟和出错面同时放大；其三，把新对象/新数组字面量作为 prop 传给子组件，每次父渲染都是新引用，hasPropsChanged 判定变化（emit 监听器除外），隔离渲染的子组件被迫重渲染——列表场景下行内处理器捕获循环变量导致未缓存，是同一问题的高频变体。

2.3 主线程瓶颈定位。可能的瓶颈按段分：事件回调自身的同步计算；pre watcher 扇出（几百个独立 job 的调度+执行）；渲染函数 vnode 生成（与模板动态节点数量相关，v-memo/patchFlag 影响这一段）；patch 与 DOM 操作（与真实变更的 DOM 节点数相关）；post 回调里的布局测量；以及任何一段中穿插的强制同步布局。单次交互不存在"分摊到多帧"的天然机会，INP 是硬截止。

3. 场景 (c)：高频持续执行（定时器、动画帧、流式数据推送）

3.1 调用发生在哪个阶段。setInterval/setTimeout 的回调各自是独立任务，任务结束后跟着一次微任务 flush；requestAnimationFrame 回调在每帧绘制前的统一时机执行，其内写入引发的微任务 flush 与随后的样式/布局/绘制处于同一帧内；WebSocket/MessageChannel 推送到达也是独立任务，突发批量消息若在同一个任务内处理，其写入会共享一次 flush，若分散在多个任务则触发多次 flush。三类源都不自动合帧，合帧必须自己在写入响应式状态之前做缓冲。

3.2 与响应式系统的交互。每 tick 一次完整 (b) 链路：高频下 pre watcher 扇出与渲染 job 持续占满主线程，flush:'post' 的 DOM 测量逻辑每帧跑；用深层 reactive 大对象承载逐帧变化的数据，Proxy 访问成本随帧率线性累计；动画类高频变更（拖拽、进度、光标）走响应式→vnode→patch 链路尤其浪费，因为真实需求只是改一个 DOM 属性。流数据若每包都替换响应式数组，watch 抖动频率等于消息频率，没有背压与聚批。

3.3 主线程瓶颈定位。持续性场景的关键不是单次耗时而是帧预算：60Hz 下每帧总预算约 16.7ms，浏览器合成/绘制需要占一半，JS（rAF 回调 + 微任务 flush + post 回调）建议控制在约 8–10ms；任何一帧超出预算即掉帧，连续超出即 Long Task。定时器场景还有"不对齐绘制"的额外浪费（一秒 flush 30 次但其中多次结果从未被绘制采纳）。

4. 三场景差异对照

4.1 (a) 的核心是"一个超长同步任务挡住首帧"，合法策略是切片让出主线程、延后非关键注册，允许总耗时不变但可感知性能大幅改善。

4.2 (b) 的核心是"一次交互的硬延迟"，让出主线程本身会增加 INP，策略是消除/合并/短路函数，而不是把它们推迟。

4.3 (c) 的核心是"每帧预算的持续达成"，策略是聚批到帧、降低每次 flush 的工作量、以及把不需要走视图链路的更新移出响应式系统。

二、风险与陷阱清单

1. 陷阱一："把函数本身 postMessage 到 Web Worker 执行"。不成立。postMessage 走结构化克隆算法，函数不可克隆，直接抛 DataCloneError；函数的闭包捕获了 Vue 的 reactive Proxy、组件实例、DOM 节点，这些在 worker 中既不存在也不可传输。能 offload 的从来不是"正在运行的函数对象"，而是"一段独立模块的代码 + 一份可序列化的入参"。worker 与主线程共享无关内存，每次调用都有序列化、事件循环投递、再序列化回传三段固定成本，小规模任务反而更慢。〔验证：构造 100 次空入参 worker 往返并在主线程直接执行同逻辑，用 performance.now() 对比中位耗时；再尝试传函数观察 DataCloneError。〕

2. 陷阱二："全局换 shallowRef/markRaw 就会变快"。shallowRef 只对 .value 的整体替换敏感，对 .value 内部属性的深层修改不收集依赖也不触发更新，盲目替换的直接后果是数据变了视图不动；补救手段是手动 triggerRef，但这要求每处修改都遵守"改完手动触发"的纪律，漏一处就是静默 stale view。markRaw 对象即便被嵌套进 reactive 也永远不会被代理，模板若依赖其属性变化同样永不更新。这类优化只在"大块只读数据"或"我明确持有批量触发点"时成立。〔验证：把同一组件改成 shallowRef 后跑功能回归用例，并在更新路径打 performance.mark 确认 trigger 次数；视图静默不更新即误用。〕

3. 陷阱三：对 computed 惰性与脏检查的三种典型误解。误解 A："computed 有缓存所以比方法调用快"——一次 flush 中只被读取一次时，computed 等于函数调用外加版本检查开销，没有收益，只有"同一依赖快照下被读取多次"才省。误解 B："依赖一变 computed 就立刻重算"——错，computed 惰性，没人读 .value 它就不执行，因此绝不能在 getter 里写副作用（发请求、打日志、改状态），副作用执行时机会随读取方变化甚至不执行。误解 C："computed 脏了就会触发组件重渲染"——3.5 中只有 getter 返回值通过 Object.is 判定变化才自增 dep.version 向下游传播；getter 里每次返回新 filter()/map() 数组或新对象，引用必变，等价于每次都强制下游更新，缓存形同虚设。〔验证：在 computed getter 内放计数器，分别在"无读取方""单次读取""两次读取"三种情况下触发依赖变更，观察计数；再让 getter 恒定返回新数组，用渲染计数观察下游是否仍每次重渲染。〕

4. 陷阱四："把 watch 改成 flush:'sync' 响应更快"。sync watcher 在依赖变更的同一调用栈立即执行，绕开了微任务合批与去重：循环里同步改 N 次 source，回调就同步跑 N 次（pre/post 模式下只跑 1 次）；它还可能在 DOM 与其他 watcher 状态都未更新的中间态被调用，读到半更新数据；级联触发时调用栈深度线性增长，异常会直接打断外层业务事务。"更快"的表象只是把等待微任务的零点几毫秒提前，代价是 N 倍执行次数。唯一正当用途是极少数需要在状态外溢前同步拦截的场景（如同步校验/状态机回滚），且回调必须极简、不级联写。〔验证：同一 source 循环写入 1000 次，分别用 pre/sync 统计回调执行次数与总耗时；用 performance 面板对比调用栈深度。〕

5. 陷阱五："用 requestIdleCallback 延迟交互关键工作"。rIC 的调度语义是"浏览器空闲时"，主线程繁忙时回调可以被无限期推迟（timeRemaining() 持续为 0），它不对齐帧、不保证在下次绘制前执行，设置 timeout 也只是在饿死时抢跑且仍可能落在帧预算外；Safari 对该 API 的支持长期缺失/版本参差，必须有降级。交互关键路径（用户点击后必须看到的反馈）应当用同步执行或 rAF/优先级调度，rIC 只适合日志上报、预取、非关键缓存预热这类丢一次也无所谓的工作。〔验证：在持续 rAF 负载下分别用 rIC 与 rAF 投递 100 个任务，统计首次执行延迟的 P50/P95；rIC 的 P95 应显著发散。〕

6. 陷阱六："上虚拟滚动就能解决几百个函数执行"。虚拟滚动只削减"已渲染 DOM 节点数"，从而降低 vnode 生成、patch、布局内存；若几百个函数是聚合计算、数据归一化、watcher 扇出、Worker 外的业务逻辑，虚拟滚动后它们一次不少地执行，且新增了滚动位置计算、监听、撑开容器、快速滚动白屏等成本。它只在"瓶颈经 profiling 证明与长列表 DOM 规模相关"时才是对症药。〔验证：Performance 面板分别记录开启虚拟滚动前后的单次交互 self time，按函数归属拆分；非渲染类函数耗时不下降即证明非对症。〕

7. 陷阱七："组件拆得越细，更新越快"。组件隔离是真实的（子组件只在 props 判定变化、自身依赖变化或强制更新时重渲染），但每个组件实例都有 vnode、render effect、props 比对、生命周期的固定成本；几百个每项一个的微型组件会显著抬高挂载开销与内存。拆分粒度应由"失效边界"决定（哪块状态变化应该只重渲染哪块视图），不是越小越好。〔验证：同一列表分别实现为单组件大 v-for 与行组件版本，对比挂载耗时与单次更新耗时两条曲线，取交点。〕

8. 陷阱八："deep:true watch 大对象很省心"。deep watch 在每次执行的取值阶段会遍历 source 的整个可达对象图以收集全部深层依赖，对象越大、触发越频繁，成本越高；它还把几百个属性都变成订阅源，任一处写入都唤醒回调。替代方案是 watch 具体路径的 getter、watch(() => ({ a: x.a, b: x.b })) 精确订阅、或 shallowRef 整体替换后在回调中自行 diff。〔验证：对同一万级对象分别用 deep watch 与精确 getter watch，打 performance.measure 测一次触发的回调前置耗时。〕

9. 陷阱九："防抖/rAF 包一层就能优化单次连锁执行"。防抖与节流只压缩"重复触发次数"，对单次交互内几百个函数的扇出总量毫无削减，反而引入可感知延迟（input 场景直接恶化 INP），rAF 包裹还把本可在事件任务内完成的工作推迟到下一帧，呈现时间晚一帧。它们是 (c) 场景聚批的工具，不是 (b) 场景减负的工具。〔验证：对单次点击场景加 debounce 测量总工作量不变、INP 升高；对连续输入场景测量回调次数下降，区分两种结论。〕

10. 陷阱十："几百个 watch 各自独立注册没关系"。没有统一生命周期归属的 watcher 会在组件卸载后继续持有闭包（回调引用组件状态、回调注册在外层单例上时），造成内存泄漏与"卸载后仍写状态"的告警；高频推送场景里泄漏 watcher 仍被触发，性能随停留时长持续恶化。必须用 effectScope/onScopeDispose（或 onWatcherCleanup）统一回收。〔验证：反复挂载/卸载页面 20 次，DevTools Memory 拍堆快照对比 Detached DOM 与监听器数量是否单调增长。〕

三、分层优化方案

架构层

1. 先分类再优化：把"几百个函数"按两个轴归类。轴一，与视图的关系：驱动渲染（其输出进响应式状态）/ 纯计算（可纯函数化、可记忆化）/ 副作用（I/O、订阅、定时器）。轴二，与关键路径的关系：首帧关键、交互关键、可延后、持续后台。分类结论决定手段：纯计算走记忆化与依赖合并，副作用走 effectScope 生命周期管理，可延后走切片调度，纯视图无关重计算走 Worker。

2. 渲染粒度与状态边界同构设计：让状态的失效范围与视图块一一对应，高频变化的状态（光标、进度、逐帧数值）与低频状态（配置、列表数据）不放进同一个 reactive 对象，避免低频组件被高频写入带着重渲染；列表项把"会变化的项内状态"与"行组件"对齐，使更新天然隔离。

3. 数据进入响应式系统之前完成归一化：把后端/流数据的解析、扁平化、索引建立放在普通对象与函数上（非 Proxy），产出结果再整体 shallowRef 替换；避免让模板渲染过程承担 join、去重、排序。配合以数据 id 为主键的 Map 索引，把几百处 O(n) 查找变 O(1)。

4. 演示级项目的架构纪律：用一个轻量任务注册中心（纯 TS，零依赖）显式登记初始化任务的优先级（关键/可延后/后台）与所属 scope，作为后续一切调度手段的挂载点；这一层不引入库、不引入状态管理。

框架层（Vue 3.5 具体 API 与机制）

5. effectScope + onScopeDispose 统一管理几百个副作用。集中创建的 watch/watchEffect/自定义订阅全部放进 const scope = effectScope()（组件内可直接用 setup 自动 scope，但显式 scope 便于动态启停），组件卸载时 scope.stop() 一次回收，防止第二章陷阱十的泄漏；自定义订阅（addEventListener、WebSocket、setInterval）内部用 onScopeDispose(() => ...) 注册反注册。3.5 中 effectScope 支持 pause()/resume()，watch/watchEffect 的停止句柄同样带 pause()/resume()（已核对 vue@3.5.43 源码：ReactiveEffect 与 EffectScope 均实现了该对方法，非 SSR 下 watch 返回句柄具备该方法），在组件处于隐藏 tab、弹窗关闭、虚拟滚动离屏区间内暂停其响应，可见时恢复——这是比 stop 更轻的手段，因为不销毁依赖关系、不丢状态。

6. shallowRef + 整体替换 + triggerRef 的批量更新模式。大块列表/表格数据用 const rows = shallowRef<Row[]>([])：处理流推送或批量编辑时，先对 rows.value 做普通数组操作（此时不触发任何 effect），结束后用 rows.value = next（引用替换，一次通知）或显式 triggerRef(rows) 一次，使一个 tick 内的几百次数据操作只产生一次渲染 job。若必须保留同一引用（外部持有该数组），用修改后单次 triggerRef，并在代码评审中禁止绕过该入口的直接修改（可配合工厂函数封装）。只读大对象用 markRaw 后再放进响应式容器，消除深层代理开销（前提是第二章陷阱二已确认其属性不驱动视图）。

7. computed 依赖图合并重复计算。把被多处消费、单次计算成本高的派生值（过滤、分组、聚合）收敛为少数几个 computed，利用其惰性 + 版本缓存：一次 flush 内渲染函数和其他 computed 多次读取同一只读快照时只算一次。注意三条机制约束：getter 必须纯函数；返回引用类型时保证输入不变则引用稳定（先比较主键，无变化则返回上一次数组，而不是每次 filter 新数组），否则 3.5 的 Object.is 去重失效；用 computed 串联（聚合 computed 依赖过滤 computed）形成有向无环图，避免 watch 串联造成的多轮调度（computed 链在读取时一次性求值，watch 链在 flush 中分轮执行）。

8. watch 的 flush 时机按后果选择，而非按"快慢"选择。需要拿更新后的 DOM（测量、滚动位置、第三方 DOM 库同步）用 flush:'post'；多数业务回调保持默认 pre，享受同 tick 去重合批；sync 仅用于同步拦截且回调内禁止级联写。高频推送场景用 watch(source, cb, { flush:'post' }) 配合"先聚批再写 source"，保证回调频率不超过帧率。清理逻辑优先用 onWatcherCleanup（3.5 API）注册，消除竞态（旧回调未完成时新回调触发，先执行清理）。需要暂时静默大批 watcher 时用 3.5 的 pause()/resume()，不要 stop 后重建。

9. v-memo 与组件拆分削减 patch 面。对大 v-for 中单行包含多个插值/指令、且每次更新多数行实际未变的场景，在 <div v-for="row in rows" :key="row.id" v-memo="[row.a, row.status, selectedId]"> 上使用 v-memo：依赖数组浅比较相等时，diff 直接复用旧 vnode，整个子树跳过 patch（连渲染函数分支都不执行），对几百行 × 每行几十动态节点的表格收益最大；代价是 memo 数组构造本身有成本且漏写依赖会导致 stale UI，依赖项必须从渲染实际读取的值里穷举。行组件拆分用于"行内有自身状态或行级 computed/watcher"的情形，借 props 引用比较实现失效隔离，但遵守第二章陷阱七，不为拆而拆；传给行组件的回调引用要稳定（cacheHandlers 只保证渲染函数内联表达式不引用循环变量时被缓存，列表项回调应定义成 (id) => ... 的稳定函数，模板里传 @click="onClick(row.id)" 而非每行 new 一个捕获 row 的函数）。静态内容用 v-once（整块永不更新）兜底。

10. 模板内零计算纪律。不在模板里写 .filter().map() 链与重函数调用（每次渲染、每个列表项都执行且无任何缓存）；不在 v-for 中写 :class="heavyFn(row)"；需要派生展示值时走 computed 或预处理。

代码层

11. 分批/分片执行的调度策略（主用于场景 a、c 的后台部分）。自研一个零依赖切片调度器，骨架为：维护任务队列与"当前帧是否已安排"标志；在 rAF 回调中记录 const frameStart = performance.now()，循环取任务执行，每个任务后检查 performance.now() - frameStart >= BUDGET（建议首帧 5ms、稳态 8ms，留半帧给浏览器）或队列清空；预算用尽则用 MessageChannel（宏任务，setTimeout 有 4ms 最小延迟且被节流）安排下一片，长任务之间穿插让浏览器处理输入与绘制。关键细节：分片粒度以"预算内任务数"动态确定而非拍脑袋定死每片 N 个，首片可先测单个任务均值再定批量（自适应 chunking）；必须保证每片内的响应式写入仍落在同一 tick 以复用一次 flush（片内同步完成写入，不要在片中间 await 后继续写，否则一片变多次 flush）；提供 runPriority(task, level) 让首屏关键任务先行、后台任务填充剩余预算。

12. scheduler.yield() 与自研调度器的取舍。scheduler.yield()（globalThis.scheduler?.yield）的语义是把控制权交还浏览器并在继续前优先处理输入事件，比 setTimeout(0) 更适合切片中的让位（无 4ms 节流、保持任务相对优先级），但浏览器覆盖不全（Chromium 系支持，其余需特性检测降级）。取舍：本项目零依赖约束下不 polyfill，采用能力检测——支持则每片边界 await scheduler.yield()，不支持则退到 MessageChannel 分片；无论哪种，切片循环内部都要有"可中断检查点"，不能把一个不可拆的大函数整体丢进去（先按数据维度把大函数改造成对每批 N 条数据幂等的小任务）。

13. 记忆化（memoization）的键设计与失效策略。对纯函数实现零依赖 memo：键用确定性序列化（入参为基本量则直接拼接；对象入参必须退到稳定主键 id，禁止 JSON.stringify 全量大对象当键，其成本可能高于计算本身），Map 存储。容量用 LRU 上限（如 500–2000 条，按数据规模定）防止流数据场景下缓存无限膨胀。失效三选一：版本失效（数据批次带 version，version 变整体清缓存，与 shallowRef 整体替换天然配套）、键空间失效（按实体 id 删除）、TTL（后台预热类缓存）。禁止对依赖闭包状态的"伪纯函数"做记忆化——先显式参数化。〔验证：命中率计数器 + 命中/未命中的函数耗时分布。〕

14. 依赖图拓扑排序避免重复执行。当几百个函数存在数据流依赖（归一化 → 聚合 → 派生视图模型 → 写入状态），将其建模为显式 DAG：每个节点声明输入键与输出键，Kahn 算法（零依赖几十行实现）求出执行序，同一批次只执行一次每个节点；用"脏节点"标记机制，源数据变更只标记受影响节点，下游在被需要时才重算（本质是把 watch 级联的多轮隐式调度替换为单轮显式求值）。严禁与 computed DAG 重复建设：图浅、天然响应式可表达的用第 7 条 computed；图深、节点多数无视图订阅、需要跨组件复用的才用显式 DAG。

15. 事件路径上的微优化。循环内避免重复 reactive 属性读取（读取即 track，提到局部变量）；批量写入用"先准备普通对象，最后一次赋值"；列表用稳定且唯一的 :key（id，不用 index——插入删除时 index key 导致错误复用与额外 patch）；v-once、函数引用稳定化同第 9 条。

运行时层

16. 何时才应该上 Worker。同时满足四条才上：计算可纯函数化且输出可序列化；单次数据量与计算量使序列化 + 往返成本显著小于计算成本（经验阈值：计算 10ms 以上且入参可 Transferable 或体积小，先用第 12 条测量验证）；计算不触碰 DOM 与 Vue 组件；频率上值得常驻（一次性小计算新建 Worker 的启动成本不划算）。典型适合项：大 JSON 解析、复杂排序/搜索/聚合、编解码、仿真/数据处理。不适合：需要 reactive Proxy、组件实例、DOM 几何、逐帧动画属性直写的工作。

17. 不可序列化闭包函数的改造路径（四步）。第一步，把逻辑从组件闭包中抽到独立模块（src/workers/tasks.ts），所有依赖以参数显式传入，输出以纯数据返回；第二步，用 Vite 的 new Worker(new URL('./x.worker.ts', import.meta.url), { type:'module' }) 原生语法创建（零新依赖，Vite 内置支持 worker 打包）；第三步，入参中的大缓冲用 Transferable（ArrayBuffer 的 transfer 列表）转移所有权，避免拷贝；高频小消息做客户端聚批（主线程攒一批一帧发一次），worker 回传结果带批次 id；第四步，主线程侧封装请求/响应映射（id → Promise resolver）、超时降级（worker 超时则回退主线程计算）、以及"worker 不可用时的同构主线程实现"（任务模块同构，worker 与主线程 import 同一份纯函数）。worker 内不引 vue。

18. 动画/逐帧通道不走响应式。拖拽、进度、rAF 驱动的数值（场景 c 中真正的高频项）用 el.style.transform/el.style.opacity 直写或 rAF 内改 CSS 变量，不经过 ref→render→patch（这类属性走合成器，配合 will-change/transform 可避免 layout）；需要与视图状态联动时只在动画结束（pointerup）时把终值写一次响应式状态。

19. 流数据的背压与聚批。WebSocket message 回调只做入队（普通数组），由一个 rAF 循环每帧把队列 drain 成一批 → 纯函数处理 → 一次 shallowRef 替换；积压超过阈值时按业务丢弃过期增量帧（如行情只留最新价）或合并同 id 更新（map 覆盖），从源头保证 watch/render 频率 ≤ 帧率。

四、可观测性与验证方案

1. 优化前定位流程（先测量后动手，禁止无 profile 优化）

1.1 埋点：在关键阶段打 performance.mark('app:setup:start') 等标记，结束处 performance.measure('app:setup', ...)；三类入口分别埋点——挂载（main.ts mount 前后、App setup、各 onMounted）、交互（事件回调首行到 post watch 回调末行）、帧（rAF 回调与 drain 批处理）。用 PerformanceObserver 订阅 entryType:'longtask'（duration、startTime、容器 attribution）与 'measure' 上报，开发期直接 console.table。

1.2 工具链：Chrome Performance 面板录制三类场景各一次，用 Bottom-Up 按 self time 排序找叶子函数（self time 高的才是真凶），用 Call Tree/Event Log 看 total time 归属（total time 高但 self time 低说明是编排/等待，应优化结构而非该函数本身）；Main 线程轨道上识别长任务与紫色 Layout（强制同步布局会标紫色警示）；Vue DevTools 的 Timeline/Performance（组件渲染事件）看每次更新渲染了哪些组件、各耗时多少，以及渲染触发次数是否与预期一致；Highlight updates 开启后操作页面，被重绘的组件以高亮闪烁，意外闪烁的大块区域即为失效边界设计错误。Memory 面板做卸载前后的堆快照对比与三次快照法查泄漏。

1.3 基线归档：每个场景记录一组数（见第 3 条），优化后同样口径复测；所有"更快/更慢"结论只认同机、同数据量、多次采样中位数对比，单次录制不作为结论。

2. 针对性指标与判读

2.1 Long Task（>50ms）：数个数、总时长、最大时长；场景 (a) 看挂载阶段长任务是否被切成 <50ms 的多段（总时长可不变，关键是首帧与可交互被提前）。

2.2 INP：用真实交互（点击/输入/键盘）在 Performance 面板或 web-vitals 思路下测交互延迟三段（input delay、processing、presentation delay）；本项目不引依赖，可用 Event Timing API（PerformanceObserver 订阅 'event'，读 processingStart 与 startTime 之差、duration 与 cancellation 标志）自行采集 P75/P95，定位瓶颈落在三段中的哪一段。

2.3 Vue 层面计数：临时用 app.config.performance = true（配合 Performance 面板的 Vue 计时轨道）或在组件内对渲染函数执行计数（render 后递增计数器/DevTools 时间线），量化"一次交互实际重渲染的组件数"——这是验证 props 稳定性、v-memo、shallowRef 替换是否生效的硬指标；watcher 触发次数同样可计数，验证合批与 pause/resume。

2.4 帧健康：rAF 中统计帧间隔，输出超过帧预算（60Hz 为 16.7ms，高刷屏以实测刷新率换算）的丢帧比例与最长帧；区分 JS 超时与样式/布局/绘制超时（Performance 面板各轨道颜色）。

2.5 self time 与 total time 的区分原则：self time 高 → 该函数自身计算重，适用记忆化/Worker/算法优化；total time 高 self time 低 → 它在调度几百个子任务，适用去扇出、拓扑合并、减少组件渲染数；patch 相关 total time 高 → 用 v-memo/虚拟滚动/减少 DOM 变更。归类错误会导致"优化了一个调度函数本身"的无效劳动。

3. 量化验收标准建议（中端移动设备口径取 P95；桌面可再收紧）

3.1 场景 (a)：首屏关键内容绘制前无单个 >50ms 的 JS 长任务（切片后每片 JS ≤8ms）；从 mount 调用到首帧（FP/FCP 用 Lighthouse/Performance 读）较基线改善 ≥30%；可延后任务不阻塞首次输入（TBT 较基线下降，首个长任务结束时间早于 FCP）；总工作量（所有 measure 之和）允许基本不变——此场景优化的是可感知时序而非总量。

3.2 场景 (b)：核心交互 INP P75 ≤200ms（"良好"线），P95 ≤300ms 作为验收红线；目标值桌面端 P95 ≤100ms；单次交互触发的组件渲染数相对基线下降（具体百分比由基线定，目标是"只渲染实际受影响节点"）；无 sync watcher 导致的重复回调（回调计数 = 逻辑变更次数）。

3.3 场景 (c)：稳态每帧 JS（rAF 回调 + flush + post 合计）≤8ms@60Hz，丢帧率 <5%，无连续 3 帧以上超时；无 Long Task；watcher/render 频率 ≤ 显示帧率（用计数验证聚批生效）；连续运行 60s 堆内存平稳（GC 后不单调增长）。

3.4 通用回归线：功能行为零变化（第二章各陷阱均有对应功能回归点）；包体积零增加（npm run build 产物对比，符合零新依赖约束）；卸载后无残留订阅（堆快照验证）。

五、取舍与决策表

说明：每行给出收益 / 成本 / 风险 / 适用场景 / 不适用场景五要素，末尾标注本演示项目的处置（实现 / 仅方案演示）。手段编号与第三章对应。

1. 任务分级注册中心（架构层，对应三-架构-4）
收益：所有优化有统一挂载点，优先级可执行。成本：一个轻量 TS 模块与任务登记改造。风险：登记纪律不执行则形同虚设。适用：初始化任务几百个且优先级混杂。不适用：函数数少、全部首屏关键。处置：实现（投入小、贯穿全场）。

2. effectScope + onScopeDispose 统一回收（框架层）
收益：根除监听器/定时器泄漏，销毁一行收口。成本：低，主要是改写注册位置。风险：scope 边界划错会误停仍需存活的副作用。适用：动态/集中注册大量副作用。不适用：组件内简单两三个 watch（setup scope 已自动处理）。处置：实现。

3. watcher pause()/resume()（3.5 新增能力，框架层）
收益：隐藏期间零触发且不丢依赖关系。成本：低。风险：恢复时机错误导致错过必须响应的变更。适用：tab 切换、弹窗、离屏行。不适用：始终可见、始终需要后台计算的视图。处置：实现（API 已存在，演示价值高）。

4. shallowRef + 整体替换 / 单次 triggerRef（框架层）
收益：几百次数据操作合并为一次通知与一次渲染，Proxy 深层开销消失。成本：中，需改造所有写入口并约束纪律。风险：漏 trigger 导致视图静默不更新（陷阱二）。适用：大列表/表格/流数据批量更新。不适用：大量分散的细粒度双向绑定表单。处置：实现（场景 a、c 的主力手段）。

5. markRaw 只读大对象（框架层）
收益：消除深层代理与内存翻倍。成本：极低。风险：误用在可变视图数据上则永不更新。适用：静态字典、一次性渲染数据。不适用：任何属性变化要反映到视图的对象。处置：实现。

6. computed 依赖图合并（框架层）
收益：一次 flush 内多次读取零重复计算，声明式、零调度代码。成本：低到中（需引用稳定化纪律）。风险：getter 不纯、每次返回新引用使缓存失效（陷阱三）。适用：多处消费的派生列表/聚合。不适用：只被读取一次、或内含副作用。处置：实现。

7. flush:'post' / pre / sync 的正确分流（框架层）
收益：消除 sync 重复执行、让 DOM 测量在正确时机做。成本：极低（选项级修改）。风险：post 用在需要阻断状态流转的场景会晚一拍。适用：post 用于测量与高频聚批回调；sync 仅用于同步拦截。不适用：sync 用于常规业务监听。处置：实现。

8. onWatcherCleanup 竞态清理（框架层）
收益：消除快触发下的过期回调写入。成本：极低。风险：几乎无。适用：watch 内触发异步操作。不适用：纯同步回调。处置：实现。

9. v-memo 列表子树跳过（框架层）
收益：大表格单次更新 patch 成本数量级下降。成本：中（每个使用点设计依赖数组）。风险：漏依赖产生 stale UI。适用：行多、每行节点多、多数行每次未变。不适用：行少或每次全量变化。处置：实现（构造一个几百行表格 demo 演示前后对比）。

10. 行组件拆分做失效隔离（框架层）
收益：高频行内更新不触发父与兄弟。成本：中，实例数量带来挂载与内存固定开销。风险：过度拆分反伤挂载（陷阱七），props 字面量新引用导致隔离失效。适用：行内有独立状态/逻辑。不适用：纯展示小行。处置：有条件实现（仅在 v-memo 无法表达的交互行使用）。

11. 渲染前数据归一化 + id 索引（架构层）
收益：O(n) 查找降 O(1)，渲染函数变薄。成本：中。风险：索引与数据一致性维护。适用：几百到上万实体的关联数据。不适用：小数据集。处置：实现。

12. rAF + MessageChannel 自适应分片调度器（代码层）
收益：长任务被切碎，首帧与输入不再被阻塞。成本：中高（调度、取消、错误传播、顺序保证）。风险：分片任务内跨 await 写状态导致多次 flush、任务有隐式顺序依赖时出错。适用：场景 (a) 与后台预热。不适用：场景 (b) 单次交互关键路径（切片增加呈现延迟）。处置：实现一个最简版用于首屏延后任务；复杂优先级队列仅方案演示。

13. scheduler.yield() 让位（代码层）
收益：输入优先、无 4ms 节流，让位质量最好。成本：低（特性检测 + 降级）。风险：浏览器覆盖不全。适用：分片边界。不适用：不可降级且要求逐帧确定时序的场景。处置：实现（带 MessageChannel 降级）。

14. requestIdleCallback 后台任务（代码层）
收益：真正不抢占交互与帧。成本：低。风险：繁忙时饿死、Safari 兼容（陷阱五），必须降级。适用：日志、预取、缓存预热。不适用：交互关键反馈。处置：仅用于非关键演示任务并带降级。

15. LRU 记忆化（代码层）
收益：重复输入纯计算近零成本。成本：低。风险：键设计错误（JSON 大键）、缓存膨胀、伪纯函数。适用：归一化/聚合/解析。不适用：一次性输入或副作用函数。处置：实现。

16. 显式 DAG 拓扑调度（代码层）
收益：深依赖链路单轮求值、节点去重。成本：高（建模、声明、与响应式的边界）。风险：与 computed 图重复建设、调试复杂。适用：跨组件、多数节点无视图订阅的深计算图。不适用：浅链路（用 computed 即可）。处置：仅方案演示，不在演示项目实现（过度设计）。

17. Web Worker offload（运行时层）
收益：重计算彻底离开主线程，帧与 INP 不受影响。成本：高（模块化改造、序列化协议、超时降级、同构实现）。风险：小任务得不偿失、闭包/DOM 依赖无法迁移（陷阱一）。适用：10ms 以上纯数据计算且可序列化。不适用：DOM/响应式绑定、逐帧小更新。处置：仅方案演示加一个独立对比 PoC（同任务主线程 vs worker 耗时对比），不接入主流程。

18. 逐帧属性直写 DOM / CSS 变量（运行时层）
收益：动画绕开 render/patch，走合成器。成本：低。风险：脱离响应式后状态一致性需在动画结束同步回。适用：拖拽、进度、光标。不适用：低频内容更新。处置：实现（若 demo 含动画场景）。

19. 流数据聚批 + 背压（运行时层）
收益：渲染频率封顶为帧率，CPU 平稳。成本：中。风险：聚批窗口增加最多一帧延迟，过期策略需业务确认。适用：WebSocket/高频推送。不适用：低频消息（每条一帧也不超载）。处置：实现（对接场景 c demo）。

20. 虚拟滚动（框架/运行时交叉）
收益：超长列表 DOM 与 patch 成本近常数。成本：高（撑开、定位、快速滚动白屏、测量）。风险：被误当万能药（陷阱六）、与可变行高配合复杂。适用：行数远超视口且 profiling 证明 DOM 是瓶颈。不适用：几百行（DOM 成本通常可承受）、瓶颈在非渲染计算。处置：仅方案演示，不在几百行量级的演示项目实现。

21. defineAsyncComponent 异步组件分包（框架层）
收益：首屏不挂载非关键大块，拉平初始任务。成本：中（加载态、骨架、失败态、分包后请求瀑布）。风险：用户可见区块用它会增加交互延迟。适用：首屏不可见的重型区块。不适用：首屏内容、极小组件（分包成本大于收益）。处置：仅方案演示。

22. 防抖/节流（代码层）
收益：压制重复触发次数。成本：极低。风险：单次连锁执行零减负且引入延迟（陷阱九）。适用：连续 resize/输入搜索（场景 c）。不适用：单次交互内扇出。处置：仅在真实重复触发点实现，不作为通用包装。

6. 演示级项目总体排期建议

6.1 第一批（低风险高确定性，覆盖三场景约 80% 收益）：决策表第 2、4、5、6、7、8、9、11 项加模板零计算纪律——effectScope 回收、shallowRef 批量模式、markRaw、computed 合并、watch 时机修正、onWatcherCleanup、v-memo、数据归一化。

6.2 第二批（针对场景 a/c 的时序改造）：第 1、12、13、18、19 项——任务分级、自适应分片、scheduler.yield 降级、动画直写通道、流聚批背压。

6.3 仅写进方案文档、不落地实现：第 16（DAG 调度器）、17（Worker 生产接入，保留对比 PoC）、20（虚拟滚动）、21（异步分包）——在"几百个函数、零依赖、演示级"约束下属过度设计；其存在价值是当数据量级或场景升级（万级实体、持续高频重计算、超长列表）时的升级路径。

6.4 验证关口：每批完成后按第四章第 3 条的同口径指标复测，任一项退化即回滚对应手段；所有"更快"的结论以 Long Task、INP（Event Timing 采集）、帧预算、渲染组件计数四类数据为准，不以主观流畅度为准。
